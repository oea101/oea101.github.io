Building a language model evaluation workflow—and a course around it

AI evaluation · Developer tools · Learning · 7 min read

I wanted to understand what sits beneath a model evaluation score. What does the model actually receive? How does its response become a grade? And when a score improves, which behaviors have changed?

I explored those questions with EleutherAI’s Language Model Evaluation Harness, then turned the walkthrough into a hands-on course for AI product managers. It includes ten milestones, a custom customer-support task, controlled model and prompt comparisons, and checks for reproducing the results.

One small experiment made the value of this workflow clear. On the same five customer-support cases, applying Qwen’s chat template improved exact tool calls from one out of five to three out of five. But it also broke the refund case that had previously passed. The higher score was real; so was the regression.

Here’s the code and course. Below, I’ll walk through the evaluation pipeline, the custom scorer, and what the experiments revealed. These are small teaching runs on synthetic support cases, not evidence of production readiness.

Why build this?

An AI product decision needs more than a leaderboard number. A support assistant can produce valid JSON while choosing the wrong action, or choose the right action while extracting the wrong refund amount. Those failures need different fixes.

I wanted an evaluation I could trace from a product requirement all the way to individual responses. I also wanted the learning process to be accessible to product managers: small local models, inspectable configuration, and a sequence of questions tied to product decisions.

What I built

The project combines an interactive curriculum with runnable evaluation exercises. It includes pinned model and task configurations, a custom YAML/Python task, a scorer with five diagnostic metrics, and scripts for controlled comparisons and regression checks.

The course can be taken interactively in Codex, one question at a time, or read through its lessons. The exercises use small open-weight models on a local CPU, so no model API key is required.

EleutherAI provides the underlying harness. My contribution is the course, the custom evaluation task, and the workflow around the experiments.

Data, models, and the evaluation pipeline

The exercises use Pythia-14M for an initial multiple-choice run, Pythia-70M for a larger-model comparison, and Qwen2.5-0.5B-Instruct for structured customer-support responses. The published course pins lm_eval 0.4.13, model revisions, and the PIQA dataset revision.

There are two different protocols here. For PIQA, the model scores candidate continuations by likelihood. For customer support, it generates text, which a custom scorer parses and grades. The protocol needs to match the behavior being tested.

Cases + task definition
        ↓
Rendered prompts and model requests
        ↓
Raw responses → parsing and grading
        ↓
Per-case evidence + aggregate metrics
        ↓
Comparison and regression decision

The result JSON preserves the aggregate. Sample JSONL preserves the evidence needed to explain it.

Starting with a score I could inspect

The first controlled exercise used Pythia-14M on 20 two-choice PIQA examples. Those 20 examples produced 40 likelihood requests: one for each candidate answer. The harness scored the candidates rather than asking the model to generate an answer letter.

The saved teaching run scored 65% accuracy, or 13 out of 20, with a standard error of roughly 11 percentage points. That was enough to inspect how the pipeline worked, but far too small a sample to make a broad claim about the model.

The distinction between aggregate results and sample logs mattered. The aggregate told me how many answers were correct. The sample logs let me inspect the prompts, candidate scores, and individual failures behind that number.

Turning a product requirement into an evaluation

For the custom task, I used a customer-support assistant that must return one structured tool call. Its available actions include tracking or canceling an order, creating a replacement, issuing a refund, and escalating to a human.

An expected response has a simple shape:

{"name":"track_order","arguments":{"order_id":"ORDER-123"}}

Illustrative output shape; not a quoted model response.

A single pass/fail metric would hide useful information, so I separated the evaluation into five questions:

  • Is the response valid JSON?
  • Does it follow the allowed tool schema?
  • Did it choose the correct tool?
  • Are the arguments correct?
  • Does the complete call match the reference?

These metrics diagnose different kinds of failure. They are not a strict funnel: choosing the right tool does not necessarily mean the rest of its schema is valid.

The scorer makes the final success condition explicit:

valid_tool_schema = _has_valid_tool_schema(actual)
correct_tool = isinstance(actual, dict) and actual.get("name") == expected["name"]
correct_arguments = (
    isinstance(actual, dict)
    and actual.get("arguments") == expected["arguments"]
)
exact_tool_call = valid_tool_schema and actual == expected

A formatting change with visible consequences

I compared three conditions on the same five synthetic regression cases: Pythia-70M with a plain prompt, Qwen2.5-0.5B-Instruct with a plain prompt, and the same Qwen model using its chat template.

Chart generated from the saved local result files. Each case represents 20 percentage points; these are teaching results, not production estimates.

Qwen’s plain-prompt run produced one exact call out of five. With its chat template, it produced three. Valid JSON improved from one case to all five, while correct tool selection reached four out of five.

The relevant setting in the Qwen configuration is:

apply_chat_template: true
fewshot_as_multiturn: false

The task prompt becomes a user message, and the tokenizer applies the model’s chat formatting. Comparing the two Qwen runs isolates the formatting condition; comparing Pythia with Qwen changes the model as well and is a separate comparison.

The five metrics make the improvement easier to diagnose. JSON parsing succeeded on every chat-formatted response, but only three passed the schema check. Four selected the correct tool, which means a correct tool name could still appear in an otherwise invalid call. Three matched the complete reference.

The most revealing finding was at the case level. Chat formatting fixed cancellation, replacement, and escalation. But the refund case, which passed with the plain prompt, failed with the chat template. Tracking failed in both.

Regression case Qwen, plain prompt Qwen, chat template
Track order Fail Fail
Cancel order Fail Pass
Create replacement Fail Pass
Issue refund Pass Fail
Escalate to human Fail Pass

The overall score improved while one previously successful behavior regressed. That is exactly the kind of detail I want an evaluation workflow to preserve.

Turning the walkthrough into a course

I organized the project into ten milestones. The first five build a mental model of the harness: its components, task definitions, model requests, and scoring. The next three cover a controlled run, reading its evidence, and changing one experimental factor at a time. The last two introduce the custom task and a reproducible workflow.

Each milestone connects a technical mechanism to a product question. Reading task YAML helps identify what a benchmark measures. Inspecting sample logs helps explain failures. Comparing fixed cases helps separate an improvement from a change in the test itself.

The repository includes an interactive teaching contract and facilitator material so the walkthrough can be taken one question at a time. It also works as a self-guided set of lessons.

Making the results auditable

The last part of the project focuses on reproducing an evaluation rather than just rerunning a command. The published course pins dependencies, model revisions, and evaluation inputs. It includes manifests, accepted regression thresholds, clean-checkout checks, and sample-level verification.

I also separated development, regression, and final-test data. Development examples support iteration; regression cases protect known behaviors; the final test is reserved for a predeclared decision. The course leaves that final test unrun. Because its cases are visible in the repository, it illustrates the process rather than providing a blind holdout.

What I took away

A useful evaluation connects a product requirement to cases, prompts, grading rules, and evidence that someone else can inspect. The score is only one part of that chain.

This project evaluates text representing tool calls. It does not execute the tools or test a complete agent handling failures across multiple steps. The datasets are deliberately small. The value of the exercise is learning to ask better questions of an evaluation, not declaring a model ready for production.

If you are an AI product manager who wants to understand what sits beneath a benchmark score, start with the course.

Try it locally

Clone the repository and run the setup script:

git clone https://github.com/oea101/introduction-to-language-model-evaluation-harness.git
cd introduction-to-language-model-evaluation-harness
./scripts/setup_course.sh

The setup requires Git, uv, jq, and ripgrep, internet access for the initial downloads, and roughly 5 GB of disk space. Open the folder in Codex and ask:

Start Introduction to the Language Model Evaluation Harness. Teach me interactively, one question at a time.
